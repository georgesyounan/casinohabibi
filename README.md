# Northplay Casino

Northplay is a bilingual Canadian casino prototype for simulated CAD play. English is the default and the French Canadian language selection persists in the browser.

The player lobby includes four built-in demo games using simulated funds: slot-style reels, a single-hand blackjack round, and red/black roulette. Round outcomes are generated by the local server and recorded in the demo ledger. The localized catalog supports title/provider search, category filters, newest-first or alphabetical sorting for provider preview listings, live result counts separating playable demo games from non-playable previews, empty-state recovery actions, a recently played filter for signed-in players, and favorites that sync to a signed-in player's account or stay in the browser for guests. Operator-imported provider listings are shown as preview-only cards and do not launch external games. The lobby also includes an overview of the demo flow, a daily simulated wager usage meter and account safety controls, configurable 30, 60, or 120 minute play-time reminders, a bilingual FAQ, authenticated support requests, and a contact link from the tenant's published support email. Players can file a formal complaint separately from general support requests. Player accounts support tenant-specific display names and language preferences, email verification and change, password recovery and change, data export, active-session revocation, and responsible-play controls, including one-day, seven-day, and 30-day cooling-off periods that cannot be shortened. Players can continue ticket conversations and reopen a closed request with a follow-up. Support requests show a reference number, when they were opened and last updated; the 50 most recently active requests remain visible after activity on older tickets, and conversations identify each message author with localized timestamps. Operator admins and support staff use the tenant support inbox to search, filter by topic, case type, priority, status, or assignment, page through requests by latest activity, prioritize, assign, identify complaints, add private case notes, and reply. Safer-play requests show staff only the relevant active player protections: self-exclusion, cooling-off, or a short break. The operator dashboard shows verified signups, signed-in players, first saves, and currently eligible public previews. Staff can select 7, 30, 90 or up to 366 custom calendar days in the brand’s reporting time zone. Optional activity details include account totals, simulated CAD wagers, rounds by day and game, open support tickets and provider catalogue counts. The bilingual CSV contains aggregate values for the selected brand, period and data source. The overview also indicates whether settings need publishing, whether any display-only catalog listings are enabled, and whether the signed-in staff account has two-step verification enabled, with role-aware links to relevant sections. Search matches either localized title and ignores accents.

Account breaks are available at the top of the account panel for 15 minutes or 1, 7, or 30 days. Signed-in devices, the support player record, and responsible-play tickets show the same period. Published previews, favorites, and account recovery stay available. The saved-activity history and player export flag actions recorded during a break using the original event time. The existing demo play limits and permanent self-exclusion still apply.

The **Discovery & rewards** workspace has separate pages for quest and offer publishing, communications, and receipt and support reports. The player opens the same entry in the catalogue or account to join Lobby Curator, claim a free cosmetic, equip it, or change topic and channel preferences. The default Curator badge has no stock cap or deadline. New campaigns start as drafts. Staff choose their audience, destination, quiet hours and delivery time in the brand's time zone. A due campaign checks current consent and account protection immediately before delivery. Each inbox message or claim receipt belongs to one account. A delivery with an uncertain email outcome requires staff review before any new send.

## Local development

Use Node.js 24 or newer. The project uses Node's built-in SQLite module and has no external dependencies.

### Windows

1. Install Node.js 24 or newer from the official Node.js website. Keep the option to add Node to PATH enabled.
2. In File Explorer, extract `Northplay-Casino-Windows.zip` into a new folder (Windows may name it `Northplay-Casino-Windows`). Open that folder; `Start Northplay Demo.bat` should be beside `package.json`.
3. Double-click `Start Northplay Demo.bat`. On its first run, it asks you to choose an operator email and password for `/admin`, creates the local encryption key, and saves these settings in `.env`.
4. Keep the launcher window open and use the player and Admin URLs it prints. The default is `http://localhost:3000`; if that port is busy, the launcher selects the next available port and prints the replacement URLs. Use the email and password you chose for `/admin`. New player accounts must verify their email before signing in; in this local demo, the verification link appears in the browser and server window. Once verified, the account receives $100 CAD in simulated credit.
5. Press Ctrl+C in the launcher window to stop the server. Keep `.env` private and do not delete it while keeping the demo database, because it contains the stable key used to encrypt local operator settings.

#### Windows setup help

- The local operator password prompt accepts 12–128 characters using letters, numbers, and these symbols: `! @ % $ _ . -`. It does not accept spaces or other symbols. The `$` character is allowed when typed at the secure prompt.
- If startup reports `EADDRINUSE`, another server is already using that port. Stop an older Northplay launcher with Ctrl+C, then run the launcher again. The launcher normally selects another free port automatically.
- If `/admin` says its setup is not loaded, make sure `.env` is beside `package.json` and restart the launcher so the server reads it.

#### Optional operator showcase data

For a presentation with non-empty overview and support examples, initialize a **fresh** extracted demo folder once with `Start Northplay Demo.bat`, then stop it with Ctrl+C. Double-click `Load Northplay Showcase Data.bat` in that folder, then start the launcher again. This adds eight fictional, non-login showcase accounts, 64 simulated rounds, and five sample support requests to the dashboard and support inbox. The dashboard labels these records as test data. When a fresh demo brand has no existing catalogue previews, new players and previews in that brand also belong to the test dataset. It makes no network calls. The command only runs in development and refuses to add rows if the database already contains player, ledger, or support data. Use a new extracted folder for a clean showcase database.

For a player-only preview, you can also open PowerShell in the project folder and run:

```powershell
npm run dev
```

Without the launcher or a configured `.env`, operator administration remains disabled. Imported provider credentials and catalog listings are demo records only; this project does not connect or launch external games.

### macOS or Linux

Run `npm run dev` from the project folder, then open `http://localhost:3000`.

The development database defaults to `data/northplay.sqlite`, preserving the existing local sandbox database. Copying `.env.example` creates a private local configuration file. Use a different `DATA_DIR` for an isolated local database.

### Shared catalogue workspace

With Node 24, run `npm run demo:workspace -- init ../habibi-training` once, then `npm run demo:workspace -- start ../habibi-training`. The first command creates a private baseline and an `access.json` file containing local credentials for the publisher, content editor and player. The second prints the two local brand URLs. Open `/admin` on the first brand for staff sign-in.

Both teams start with the same examples in [shared-fixtures.json](scripts/shared-fixtures.json). The player sees Club Classic. The editor also sees Studio Preview and can edit drafts. The publisher can publish them. The second brand has an empty catalogue and separate access. Stop the session with Ctrl+C and run the start command again to restore the original data. Two teams can use the same baseline concurrently by choosing different `PORT` values.

### Staging and production environments

Environment files are loaded automatically by the npm scripts. Copy `.env.staging.example` to `.env.staging`, replace the placeholders with real staging settings and secrets, then run `npm run start:staging`. Production uses `.env.production` with `npm run start:production`. Keep `.env`, `.env.staging`, and `.env.production` private; Git ignores them. The checked-in `*.example` files contain placeholders only.

Staging and production require an explicit data directory, host, valid encryption key, and `SECURE_COOKIES=1`. The server records the environment in each data directory and refuses to start if that directory is later opened under a different environment. This prevents one environment from accidentally using another environment's database. Do not point multiple environments at one `DATA_DIR`.

Startup also rejects invalid ports, malformed encryption keys, incomplete bootstrap credentials, short platform tokens, and missing required staging/production settings before it opens the database.

For a site hosted under a URL directory, set `APP_BASE_PATH` to that directory, such as `/casinohabibi`. It defaults to the path in `PUBLIC_BASE_URL` when configured. The reverse proxy may forward or strip the directory, and session cookies use that directory. For a hosted demo, `SANDBOX_TENANT_HOSTS` accepts a comma-separated list of hostnames managed by the operator. Keep the existing data directory and encryption key when updating a deployment.

## Operator administration

Open `/admin` for the Dashboard. Use the sidebar on desktop or the section picker on a phone to access the game catalogue, player activity, support, website content, staff, audit log and your security settings. Your staff role determines which sections are available. Brand, region, lobby, FAQ and policy settings share a configuration draft. In **Website content → Banner and guides**, each help page and the lobby banner have their own draft and publish action. Switch translations to edit or preview either language. The page address stays the same when its title changes. Publishing the banner replaces the default lobby hero. Unpublishing it restores the default. A link to a title or help page that becomes unavailable takes the visitor to the catalogue. Publishers can check the revision and actor in the publication history and the Audit log.

Within a guide, choose the translation and open **Page address and search preview** to edit the public address, search title and description. Publishing a renamed guide sends old links directly to the current translation. A guide can list eligible previews from a catalogue collection. The indexing checkbox applies to the whole guide at publication. The public `/sitemap.xml` under the application’s base path lists the lobby, published previews and indexable guides available to that brand and language.

To enable tenant administration manually, set `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` (at least 12 characters), and `PROVIDER_KEY_ENCRYPTION` (a 32-byte key represented by 64 hex characters) in the server environment. The Windows demo launcher can create these local settings on first run. The old shared `ADMIN_TOKEN` is no longer used. The bootstrap account is added as a sandbox operator admin if it does not already exist; its password is not reset on later starts. Generate the encryption key locally, keep it private, and retain the same key for any database you intend to keep. Open `/admin` and sign in with the bootstrap credentials. Staff can change their own password from the Admin page; the current password is required, and other sessions for that staff identity are revoked. The operator admin can add staff accounts or grant a tenant role to an existing staff identity, change active staff roles, disable accounts, and re-enable previously disabled accounts with a selected tenant role. Operators cannot change their own role or demote the last active operator admin. These staff actions are recorded in the tenant audit history. Operator admins can search and filter the history, load events in pages of 50, and export the filtered events as CSV. Provider and configuration actions require an appropriate tenant role and are recorded in tenant staff audit events. The casino settings form edits the casino name, optional locally stored PNG/JPEG/WebP logo (up to 48 KB) and PNG/WebP favicon (up to 16 KB), accent colour, support email, English and Canadian French lobby headline and introduction, an optional bilingual announcement, three editable bilingual FAQ entries, optional English and Canadian French terms and privacy links (HTTPS only), and a bilingual footer disclaimer, with a side-by-side preview before saving and publishing. Staff can enable authenticator-based two-step verification from the admin page.

The admin catalog section has a sample-data action that saves a local placeholder provider key and prepares a bilingual catalog for preview. Review the proposed changes and choose **Sync catalog** to display the listings as preview-only cards. This action does not contact an external provider or launch its games.

### Coming Soon previews

**Game catalogue → Coming Soon** shows eight records per page. Search either translation, category, studio, collection or slug and filter by publication status. Open a title to edit one translation at a time. Category, studio, visibility and cover image have their own expandable sections. The published filter includes live previews with pending draft changes. The draft-changes filter selects those previews specifically.

To group previews, enter the collection name in each language the card supports. Visitors can search the eligible published catalogue by title, category, studio or collection and return from a preview with the same filters. Withdrawn or unavailable previews offer another eligible title when one exists.

Open **Coming Soon** in **Game catalogue** to save a bilingual draft. Choose the display market and languages, then open **Preview draft** to review the artwork and copy. **Publish preview** makes that revision available in the eligible public lobby. Operator admins and staff who have catalogue publishing rights for that brand can publish or archive previews. A positive rank places a published preview in **Featured**. Each visit shows up to six eligible previews in **Discover**. Reordering Featured preserves the Discover row. Archiving replaces its open slot when another card qualifies. Visits expire after 30 minutes of inactivity.

Signed-in players can keep their previews in Favorites across devices. Each addition or removal has an activity reference. Retrying the same change preserves that reference. Archiving clears the active favorite. Staff can still search **Players** by email, player ID, `save-N` or `activity-N` and open the account history. The dashboard counts each player’s first verification once, each signed-in player visiting in the selected period once, and each player–title pair once at its first save. Published previews reflect the catalogue at the time of the report. Admins and support staff can open the matching player or saved activity from the figures. Test records have their own filter. Older accounts without a known verification date appear in the all-time total and the dashboard identifies them. For dates before visit tracking began, only retained session start times are available. The staff audit history identifies each publish or archive by actor, preview, revision and request ID.

In Windows Command Prompt, set the variables in the same window before starting the server:

```bat
set BOOTSTRAP_ADMIN_EMAIL=admin@example.ca
set BOOTSTRAP_ADMIN_PASSWORD=use-a-long-private-password
set PROVIDER_KEY_ENCRYPTION=paste-your-saved-64-character-hex-key
npm run dev
```

Replace the example email and password with private values. Create the encryption key once with PowerShell and keep it somewhere private. For example, run `$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create(); $bytes = New-Object byte[] 32; $rng.GetBytes($bytes); [BitConverter]::ToString($bytes).Replace('-', '').ToLower()` in PowerShell. Paste that output as the `PROVIDER_KEY_ENCRYPTION` value each time you open a new command window. Changing it prevents stored provider credentials and MFA secrets from being decrypted.

Roles are assigned per brand. Operator admins manage staff and have full publishing access. Content staff can edit website and catalogue drafts. Provider staff manage provider credentials and catalogue previews. Support staff handle player requests. In **Staff and permissions**, an admin can give content staff website or catalogue publishing rights and provider staff catalogue publishing rights. Existing content and provider accounts keep their prior website and catalogue publishing access respectively.

In **Website content → Display and region**, set the available site languages, default language, optional public sections, editorial display market, and reporting time zone. Changes take effect when the draft is published. The dashboard uses the published time zone for date filters and the daily chart. The market and enabled languages determine which published previews count as visible.

**Audit log** shows all brand events to admins. Publishers see their own editorial events for the areas they can publish. Changes save with an audit ID, and retries with the same `X-Request-ID` and payload return the recorded result for audited publication, staff access, and support changes. The journal stores field names and change references. Private support notes stay in the case.

Staff sessions expire after eight hours and use an HttpOnly, SameSite cookie. Set `SECURE_COOKIES=1` behind HTTPS.

## Platform tenant onboarding prototype

Set a separate `PLATFORM_ADMIN_TOKEN` with at least 32 characters to enable the platform API. Requests must use the existing mapped sandbox host (for local development, `localhost`) and send `Authorization: Bearer <PLATFORM_ADMIN_TOKEN>`. The API supports:

- `POST /api/platform/tenants` with `{ "slug": "operator-one", "name": "Operator One" }` to create a pending tenant.
- `POST /api/platform/tenants/admin` with `{ "tenantId": "…", "email": "admin@example.ca", "password": "…" }` to create the first operator admin. If the email already belongs to a staff identity, its existing password is reused and the `password` field can be omitted.
- `POST /api/platform/domains` with `{ "tenantId": "…", "host": "casino.example.ca" }` to issue a DNS ownership challenge.
- Publish the returned TXT value at the returned TXT name, then call `POST /api/platform/domains/verify` with `{ "host": "casino.example.ca" }`.
- `POST /api/platform/tenants/status` with `{ "tenantId": "…", "status": "active" }` to activate after a verified domain exists. `suspended` and `closed` are supported lifecycle states; closed tenants cannot be reopened.
- `GET /api/platform/tenants` to list tenant/domain state and `GET /api/platform/audit` to review platform lifecycle events.

This remains an early control-plane API behind one shared platform token. Tenant staff accounts and roles do not replace individually managed platform staff identities or a production identity provider.

`HOST` defaults to loopback. Keep admin access local during development. For HTTPS deployments, set `SECURE_COOKIES=1`.

## Player password recovery

New player accounts require email verification before sign-in. Verification links expire after 24 hours and can be resent from the sign-in panel. Legacy accounts are treated as verified when the verification field is added during migration. A loopback development instance can display verification links locally. Hosted instances send verification and recovery emails using the same bilingual mail transport.

Players can request an email change from account settings after entering their current password. The new address must be confirmed within 24 hours. The current address remains active until confirmation; on completion, all player sessions are revoked and the player must sign in again. The previous address receives a notice when email delivery is configured.

Casino Habibi players can register with a password or an eight-digit email code. Codes expire after ten minutes. Existing players can add a unique login username in their profile. Both sign-in and registration also support Google and Discord when the operator configures the respective provider on the canonical HTTPS host. Set `PLAYER_GOOGLE_CLIENT_ID` and `PLAYER_GOOGLE_CLIENT_SECRET` or `PLAYER_DISCORD_CLIENT_ID` and `PLAYER_DISCORD_CLIENT_SECRET` in the service environment. Register the exact return URL `<PUBLIC_BASE_URL>/api/player-auth/callback/google` or `<PUBLIC_BASE_URL>/api/player-auth/callback/discord` with the provider, including the application directory. Only configured providers are offered. A matching email alone cannot attach an external identity to an existing player.

Players can request a password reset from the sign-in panel. Reset links expire after 30 minutes, can be used once, and invalidate the account's existing sessions after a successful reset. Local loopback development can show the reset link in the browser. Set `RESET_EMAIL_FROM` and an HTTPS `PUBLIC_BASE_URL`. Choose either a Resend key in `RESET_EMAIL_API_KEY` or a local mailer in `RESET_EMAIL_SENDMAIL` (for example `/usr/sbin/sendmail` on cPanel). Passenger installations may set these mail settings in a private `.env.mail` next to `server.js`. Environment variables take precedence.

In **Players**, support staff can search for an account and send recovery to its stored email address. Operator admins and support staff explicitly granted **Suspend and restore player access** can change access with a reason. Suspending revokes sessions and pending links. Restoring access requires a fresh sign-in and preserves responsible-play exclusions.

Signed-in players can revoke other active sessions from account security settings; the current device remains signed in. They can also opt into or out of promotional email in account settings. Each consent change records the choice, time, language, notice version, and source; essential account and security emails are separate. This preference does not send marketing email until a communications service is connected. The account export includes this consent history.

The account panel shows demo activity in pages of 20 entries, with each play's date, wager, and balance change. Players can download their full demo activity as a CSV with UTC dates and CAD values, or download the complete JSON account export. Players can restore their simulated balance to $100 CAD without erasing history or resetting the daily wager limit. The JSON contains the account email, verification status, preferred language and tenant ID, simulated balance and full ledger activity, responsible-play controls (including current UTC daily wager amount/date and the selected reminder interval), consent history, and support requests with player/staff messages. Internal staff notes and credentials are excluded. The API is `GET /api/account/export` and requires the player's session cookie. The lobby language switch saves the preference to the signed-in account and restores it on future sign-ins.

## Health and request tracing

- `GET /healthz` reports that the HTTP process is responding.
- `GET /readyz` checks that the service can query its SQLite database.
- Every response includes an `X-Request-ID`. A valid UUID supplied in the incoming `X-Request-ID` is preserved; otherwise the service creates one. JSON errors include the same ID in their response body.
- The server writes one JSON request log per response with the request ID, path, method, status, duration, and resolved tenant ID when available. It does not log query strings, cookies, or request bodies.
- Staff and platform audit records include the request ID as `correlationId`, so an authorized admin can find the matching request log.

## Database backup and recovery

The database CLI uses SQLite's online backup API, so it captures a consistent snapshot even when the service is running. Each backup gets a SHA-256 manifest and is checked with SQLite integrity and foreign-key checks. It refuses to overwrite an existing backup or write one inside the live `DATA_DIR`.

Windows Command Prompt examples (run from the project folder):

```bat
npm run db:backup -- "..\northplay-backups\northplay-development.sqlite"
npm run db:verify -- "..\northplay-backups\northplay-development.sqlite"
npm run db:prepare-restore -- "..\northplay-backups\northplay-development.sqlite" "..\northplay-restore-development"
```

Staging and production use the matching scripts, such as `npm run db:backup:staging -- "D:\northplay-backups\northplay-staging.sqlite"` and `npm run db:verify:production -- "D:\northplay-backups\northplay-production.sqlite"`. The CLI checks the backup's environment manifest before preparing a restore.

`db:prepare-restore` never replaces the active database. It requires a new, empty path and prepares a separate data directory with its environment marker. For recovery, stop the service, take and verify a backup of the current database, prepare the chosen backup into a new directory, and verify the prepared database before changing `DATA_DIR` to that directory. Start the service and confirm `/readyz`; keep the previous data directory intact until the restored service is confirmed.

Backups contain player and operational data. Store them outside the application checkout with restricted access and encrypted storage, and copy them to a separate failure domain using your deployment's protected backup process. The CLI does not schedule backups, encrypt them, or delete old backups. Test restore procedures regularly in an isolated directory.

Run `node --test --test-name-pattern="P1 recovery drill" test/sandbox.test.js` for the phase-one restore drill. It creates a synthetic verified player, a saved catalogue card, a published bilingual help page and an unpublished revision. It snapshots the running test service, verifies the manifest, and starts a second local instance using the restored data and the same test encryption key. The assertions compare the original account, saved activity, revisions, audit IDs and replay receipt. The drill also changes the source after the snapshot to verify that the two instances operate independently.

The Dashboard shows **Publication follow-up** when the brand has recorded a publication problem. Administrators can review issues for the brand. Other publishers can review their own attempts within their current permissions. Search by English or French title, record ID or request reference, open the draft and publish the correction. A successful publish or withdrawal resolves outstanding attempts for the same record and action. Resolved entries retain their original reference and the audit ID when the viewer can access it.

If a catalogue or website publication fails, its editor displays a request reference. Look up the reference as `requestId` in the service's JSON log to find the brand, action, record and status. Retrying the same publication in the editor after an interrupted response or server error reuses the reference. After success, the Audit Log matches it to the committed revision. Run `node --test --test-name-pattern="website publication survives" test/sandbox.test.js` to exercise a failed publication, trace it and retry.

This prototype uses simulated funds. An operator with provider access can upload or paste a JSON catalog into the admin area; the lobby validates the bilingual titles and categories, then previews added, changed, unchanged, and removed listings before syncing. The server checks that the catalog has not changed since that preview. The protected catalog API stores listings only and does not launch games. Provider connection tests, launch sessions, and real-money services are future work.
